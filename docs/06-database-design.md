# EPIC-08 Stage 2 - Proposed Oracle Schema Design

## Status and Classification

**Stage 2 design proposal only.** No DDL is executed, no Oracle database is created or connected, and no application code is changed.

Each item is classified as:

- **CONFIRMED**: explicitly supported by requirements or current code.
- **PROPOSED**: a conservative relational design choice derived from confirmed requirements/current models.
- **TBD**: requires business or database clarification before implementation.

## 2. Global Oracle Conventions

| Item | Proposal | Classification |
|---|---|---|
| Primary key strategy | Numeric surrogate `*_ID NUMBER(19)` generated by Oracle identity or sequence | PROPOSED; exact choice TBD |
| Business identifiers | Preserve source-system/business numbers in separate columns | PROPOSED |
| String types | `VARCHAR2` lengths are provisional until source limits are known | TBD |
| Dates/times | `DATE` or `TIMESTAMP` only after timezone/date semantics are confirmed | TBD |
| Numeric fields | `NUMBER` precision/scale must be confirmed from domain units | TBD |
| Schema owner | TBD | TBD |
| Audit columns | `CREATED_AT`, `CREATED_BY`, `UPDATED_AT`, `UPDATED_BY` only where approved | PROPOSED/TBD |
| DDL execution | Not performed in Stage 2 | CONFIRMED |

Every proposed table below uses `*_ID` as a candidate surrogate key. This is not an approved physical schema.

## 5. Mapping Existing Logical Models

- `Supplier`: read from `SUPPLIER.SUPPLIER_NO` and `SUPPLIER.SUPPLIER_NAME`; current `SupplierRepository.findAll()` remains the stable boundary.
- `DsdOrderArticle`: proposed as a joined Oracle read result assembled from `ORDER_HEADER`, `ORDER_LINE`, `ARTICLE`, `SUPPLIER`, and stock sources; it is not necessarily one table.
- `StockAssignmentResult`: proposed as a joined/read result from `STOCK_ASSIGNMENT`, `ARTICLE`, `MERCH_GROUP`, `STORE_STOCK`, `DC_STOCK`, and related master data; calculations and ownership remain TBD.
- `StockAssignmentDcDetail`: proposed as a read result grouped or joined by `DISTRIBUTION_CENTER`, `DC_STOCK`, and Stock Assignment context; the current model lacks enough identity fields to finalize the relationship.

## 6. Keys, Indexes, and Generation Strategy

- Surrogate numeric primary keys using Oracle identity or sequences are proposed for all physical entities; exact sequence names and identity policy are TBD.
- Business-number unique constraints are proposed for supplier, store, DC, and parameter codes where confirmed uniqueness is approved.
- Candidate indexes include supplier/store/DC business numbers, article number, order number/list, foreign keys, assignment day, and supported lookup predicates.
- No index is confirmed until query patterns and data volumes are known.
- No unique constraint is confirmed where the source code does not establish uniqueness.

## 7. Architecture Preservation

Oracle repositories should implement the existing stable interfaces:

```scala
trait SupplierRepository {
  def findAll(): Seq[Supplier]
}

trait DsdOrderArticleRepository {
  def findAll(): Seq[DsdOrderArticle]
}

trait StockAssignmentRepository {
  def findAll(): Seq[StockAssignmentResult]
  def findDcDetails(): Seq[StockAssignmentDcDetail]
}
```

Services continue to own application-facing orchestration. Wicket pages remain unaware of JDBC and Oracle.

- Which requirement-proposed tables are required in the first release?

- What are the source-system lengths, units, currencies, and code sets?
- Which fields are persisted versus calculated?
- What are the approved natural keys and relationship cardinalities?
- Are assignment, stock, and forecast values snapshots or effective-dated facts?
- What is the authentication/password model?
- What audit events and retention rules are required?
- What transaction and locking rules apply to future writes?

## 9. Scope Boundary

Stage 2 documents a proposed schema only. It does not execute DDL, connect to Oracle, add JDBC, replace mock repositories, add PL/SQL, or modify application behavior.

## 10. Stage 3 DDL Artifact

The reviewable Stage 3 DDL artifact is:

`database/ddl/001_epic08_stage3_schema.sql`

The script follows the documented dependency order and includes the proposed
tables, documented `NOT NULL` columns, primary keys, proposed foreign keys,
proposed unique constraints, candidate indexes, and review comments. It does
not execute any DDL or select an identity-versus-sequence strategy. Identity
and sequence definitions remain non-executable placeholders because their
strategy, names, and ownership are TBD. No unresolved schema, business,
transaction, calculation, audit, or PL/SQL details are invented.
